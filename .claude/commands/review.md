あなたはシニアエンジニアとして、以下の手順でコードレビューを行ってください。

## 重要な制約

- `gh pr view` を引数なしで実行してはならない（CI では detached HEAD のため必ず失敗する）
- `--body "..."` のようにフラグ値に引用符を使ってはならない（Claude Code のセキュリティチェックで拒否される）
- `&&` や `;` でコマンドを連結してはならない（権限チェックで拒否される。必ず 1 コマンドずつ別の Bash 呼び出しで実行すること）
- PR 番号は `$ARGUMENTS` として渡される（例: `/review 51` なら `$ARGUMENTS` = `51`）
- ファイルの直接読み込みは禁止。diff の情報のみでレビューすること
- レビューは必ず「1ファイルずつ」行うこと。複数ファイルの diff をまとめて一度に評価してはならない

## 手順

### フェーズ1: 対象ファイルの特定

1. PR 番号は `$ARGUMENTS` を使う
2. `gh pr diff $ARGUMENTS --name-only` で変更ファイル一覧を確認する
3. 一覧から `package-lock.json` / `package.json` / `*.lock` などビルド成果物・依存関係ファイルを除外し、レビュー対象ファイルのリストを作る

### フェーズ2: ファイルごとのレビュー（ループ）

対象ファイルのリストを先頭から1つずつ処理する。各ファイルについて:

4. `gh pr diff $ARGUMENTS -- <ファイルパス> | wc -l` で行数を確認する
5. 400行以下ならそのまま1回でレビュー
6. 400行を超える場合、以下の手順で400行ずつに分割してレビューする:
   - 1回目: `gh pr diff $ARGUMENTS -- <ファイルパス> | sed -n '1,400p'` をレビュー
   - 2回目: `gh pr diff $ARGUMENTS -- <ファイルパス> | sed -n '401,800p'` をレビュー
   - 以降、行数(手順4で確認した値)を超えるまで、範囲を400行ずつ (801,1200p / 1201,1600p ...) とずらしながら同様に繰り返す
   - 全チャンクのレビューが終わったら、同じファイルの指摘として1つにまとめる
7. 次のファイルに進み、全対象ファイルを処理し終えるまで4〜6を繰り返す

重要: 1回のレビューで見るのは常に1ファイル分の diff のみ。他ファイルの diff を混ぜて評価しないこと。これにより大きな PR でも各ファイルへの指摘の解像度を落とさない。

### フェーズ3: 集約と投稿

8. 全ファイルのレビューが終わったら、保持していた各ファイルの指摘を集約し、`Write` ツールで一度だけ `/tmp/review-comment.md` に保存する（出力フォーマットは下記）
9. `gh pr comment $ARGUMENTS --body-file /tmp/review-comment.md` でコメントを投稿する
10. **必須**: 全ファイルを通して 🔴 Critical が「なし」であれば `gh pr review $ARGUMENTS --approve` を実行する。1件でも Critical があれば実行しない。この手順はスキップしてはならない。

## チェックリスト（各ファイルに適用）

### 🔴 Critical（必ず修正）

- セキュリティ脆弱性（XSS, SQL Injection, 機密情報の露出など）
- 型安全性を壊す `any` の使用
- 未処理の Promise / エラーハンドリングの欠如
- 本番環境に影響するバグ

### 🟡 Warning（修正を推奨）

- TypeScript の型が不正確・不十分
- React のベストプラクティス違反（useEffect の deps 漏れ、不要な再レンダリングなど）
- 重複コード・責務の混在
- テストが書かれていない重要なロジック

### 🔵 Suggestion（改善提案）

- 可読性・命名の改善
- パフォーマンスの最適化余地
- コンポーネント分割の提案

## このプロジェクト固有の観点

- **Next.js App Router**: Server Component と Client Component の使い分けが適切か
- **Supabase**: RLS（Row Level Security）に依存した操作になっているか、直接 Service Role Key を使っていないか
- **Apollo Client**: キャッシュ戦略は適切か、不要なリクエストが発生していないか
- **GraphQL**: 型生成（codegen）を活用しているか、`any` で逃げていないか
- **MUI**: テーマに沿ったスタイリングになっているか
- **ESLint**: ルール違反がないか、特にセキュリティ関連のルールは守られているか
- **Accessibility**: ARIA 属性の適切な使用、キーボード操作のサポートなど
